# Spring MVC. Валидация. Интеграция Jakarta Validation

В текущей статье рассмотрим две родственные темы:

- Подключение Jakarta Validation к Spring MVC, основные операции по конфигурации и использованию валидатора в
  бэкенд-приложениях на базе Spring;
- Внутренний механизм валидации, предоставляемый Spring MVC.

Статья во многом проходная - с точки зрения практического применения, бОльшая часть функций основана на уже известной
нам спецификации Jakarta Validation, чисто спринговых особенностей здесь не так много и направлены они преимущественно
на сокрытие императивной настройки в пользу декларативного формата.

Однако в данном случае это к лучшему - мы сможем больше внимания уделить примерам и базовым сценариям использования, не
уходя в дебри внутренней реализации и побочных инструментов. В конце концов, обычно бэкенд-разработчик
сталкивается с Jakarta Validation именно в разрезе Spring MVC.

Также в этой статье практически не будет специфики, характерной для view based подхода в Spring MVC - основной упор
будет сделан именно на подходы, характерные для REST API.

## Актуальность

Говоря о связке Spring MVC (или Spring в целом) + Jakarta Validation можно вывести относительно небольшой набор
сценариев использования, наиболее популярных в реальной разработке:

- Валидация входящих HTTP-запросов. Внутри себя этот сценарий разделяется на валидацию тела запроса и других элементов
  HTTP-запроса. Эти подходы используют разные механизмы на уровне Spring MVC, в статье рассматриваются оба;
- Иногда Jakarta Validation используется для валидации ответов внешнего сервера при работе с HTTP-клиентами. Этот
  сценарий намного менее популярен, нежели предыдущий, но не менее полезен. Это позволяет как отлавливать ошибки раньше,
  чем обработка ответа дойдет до уровня бизнес-логики, так и в принципе получать информацию о некорректной реализации
  контракта взаимодействия между приложениями;
- Валидация моделей БД - JPA Entities или аналогичных по смыслу классов, если JPA не используется. Изначально именно
  отсюда и выросла наиболее известная реализация Jakarta Validation - Hibernate Validator, однако на практике этот
  подход менее популярен, нежели валидация запросов. При этом валидация моделей БД сама по себе не отменяет валидации
  входящих запросов или входящих ответов - это отдельные задачи со своими зонами ответственности. Но зачастую в
  приложении осознанно отказываются от проверки классов-моделей уровня работы с БД, предполагая, что подобная валидация
  в норме должна производиться на уровне домена или бизнес-логики приложения, а последним рубежом обороны от
  некорректных данных выступают constraint'ы в самой базе данных;
- Наименее популярными, но возможными сценариями можно называть валидация исходящих ответов, исходящих запросов и
  параметров методов внутри приложения (не считая слой контроллеров). Все эти сценарии схожи тем, что в норме данные уже
  должны быть валидны - эти гарантии ожидаются от предыдущих слоев обработки. Ведь формировать, скажем, невалидный
  ответ - в принципе неправильно, проблему логично определить как можно ближе к моменту ее возникновения. Однако в
  отдельных случаях такие подходы имеют смысл, особенно в больших многомодульных приложениях, где один модуль может не
  доверять другому - скажем, потому что разные модули делают разные команды. В современной разработке такое встречается
  крайне редко, однако для legacy-проектов это может оказаться суровой реальностью.

## Подключение

### Зависимости

В Gradle-конфигурации все просто: требуется добавить провайдера Jakarta Validation (он также транзитивно подтянет
спецификацию) и реализацию для Jakarta EL - это ничем не отличается от того, как подключается Jakarta Validation в
обычное приложение без Spring:

```groovy
implementation 'org.hibernate.validator:hibernate-validator:9.1.2.Final'
implementation 'org.glassfish.expressly:expressly:6.0.0'
```

### Конфигурация валидатора в приложении

При наличии `@EnableWebMvc` Spring самостоятельно регистрирует валидатор, если видит Jakarta Validation в classpath -
для этого в Spring Context присутствует `OptionalValidatorFactoryBean`. То есть в самом базовом сценарии ничего 
дополнительно не требуется и валидация будет доступна из коробки.

Однако в более специфичных случаях - необходимость явного внедрения `Validator` в коде или же при нестандартных
настройках `Validator`, `ConstraintValidatorFactory` и спринговых оберток для валидаторов потребуется ручная
регистрация.

Выглядеть это может так:

```java
// Аннотации стандартные для веб-конфигурации, мы уже рассматривали их ранее
@Configuration
@EnableWebMvc
@ComponentScan("com.walking.validation")
// Интерфейс WebMvcConfigurer уже несколько раз упоминался в более ранних статьях, но не использовался.
// Более подробно мы рассмотрим возможности интерфейса в статье, посвященной тонкой настройке Spring MVC.
// Здесь он необходим для регистрации валидатора 
public class WebConfig implements WebMvcConfigurer {
    @Bean
    // LocalValidatorFactoryBean - центральный объект Spring для работы и с Jakarta Validation, и с собственным 
    // механизмом валидации в Spring. Упомянутый ранее OptionalValidatorFactoryBean - прямой наследник данного класса.
    // Под капотом он создаст и ConstraintValidatorFactory, и, соответственно, сам Validator
    public LocalValidatorFactoryBean validator() {
        return new LocalValidatorFactoryBean();
    }

    @Override
    // Сообщаем Spring MVC о ранее зарегистрированном бине. Механизмы валидации для контроллеров будут получать
    // валидатор именно через этот метод
    public Validator getValidator() {
        return validator();
    }
}
```

Еще один класс, который нам интересен с точки зрения конфигурации валидатора в Spring -
`SpringConstraintValidatorFactory`. Он является наследником `ConstraintValidatorFactory`, уже знакомого нам из
статьи о Jakarta Validation. `SpringConstraintValidatorFactory` обычно не используют напрямую, но он необходим
`LocalValidatorFactoryBean` для того, чтобы подружить Jakarta Validation и Spring-контекст. Данная реализация
фабрики позволяет использовать внедрение зависимостей в `ConstraintValidator`. Иными словами, становится доступно
использование Spring-бинов при обработке собственных constraint-аннотаций. Ниже мы рассмотрим пример такого
использования.

## Базовый API

Рассмотрим использование Jakarta Validation в Spring MVC для валидации запросов.

Как было упомянуто ранее, здесь стоит разделять валидацию тела запроса и других параметров метода контроллера.
Разработчики запоминают примерно так, но правильнее будет исходить из реализации различных
`HandlerMethodArgumentResolver`.

### Валидация через `DataBinder`

Так, одна группа представлена реализациями `HandlerMethodArgumentResolver`, которые так или иначе вызывают
`DataBinder#validate(Object... validationHints)`. С самим классом `DataBinder` и его наследниками мы сталкивались
при знакомстве с `DispatcherServlet`. К этой группе можно отнести следующие параметры методов контроллера:

- Аннотированные `@RequestBody`. Наиболее популярная опция, именно с телом запроса мы будем работать в примерах в
  первую очередь;
- Аннотированные `@RequestPart`. Ранее мы использовали его для загрузки файлов, но этим его зона применения не
  ограничивается;
- Аннотированные `@ModelAttribute`. С аннотацией мы тоже поверхностно знакомы. Но поскольку она относится в первую
  очередь к классическому подходу Spring MVC, встретить ее на практике с каждым годом все сложнее;
- Параметры типов `HttpEntity` и `RequestEntity`;
- Параметры, представленные классами-моделями, не помеченные отдельной аннотацией. Таким образом оформляют
  URL-encoded формы или параметры запроса, если их слишком много или по каким-то иным причинам не хочется указывать
  каждый по отдельности. Также рассмотрим в примерах.

Параметры этой группы будут провалидированы, если выполняется условие, описанное в
`ValidationAnnotationUtils#determineValidationHints()`. Его можно описать примерно так:

- Параметр аннотирован `@Validated` (из пакета `org.springframework.validation.annotation`). Это именно аннотация
  Spring, она не имеет прямой связи с Jakarta Validation. Саму аннотацию мы встретим как минимум в двух разных
  сценариях использования;
- Или параметр аннотирован любой аннотацией, которая содержит вышеупомянутую `@Validated` в качестве мета-аннотации;
- Или параметр аннотирован `@Valid` (из `jakarta.validation`). С этой аннотацией мы хорошо знакомы;
- Или параметр аннотирован любой аннотацией, имя которой начинается с `Valid`. Это было сделано в первую очередь для
  совместимости со старыми версиями Jakarta Validation - у них различается пакет (`javax.validation`). Но в целом
  эта особенность оставляет пространство для фантазии и под другие ситуации.

Рассмотрим наиболее общий пример. Допустим, мы разрабатываем приложение, обрабатывающее некие заказы: у нас есть
API для создания, обновления и поиска заказов, также есть потребность валидировать содержимое запросов.

> **!NB**: практически все примеры кода в этой статье можно увидеть собранными воедино в отдельном репозитории -
> ссылка на него приложена в конце статьи.
>
> Важно отметить, что все примеры направлены строго на демонстрацию механизмов валидации. Чтобы не перегружать
> примеры спецификой предметной области и сложной бизнес-логикой, многие вещи упрощены до неприличия. Так, в
> примерах мы практически во всем доверяем клиенту (верим, что он не будет умышленно искажать значения атрибутов,
> которые в норме должны изменяться строго на бэкенде), также замоканы части приложения, не относящиеся к теме
> напрямую - обращение к внешним сервисам, работа с БД и так далее.
>
> Не стоит воспринимать код примеров, как образцы хорошей архитектуры. Их задача - продемонстрировать работу
> валидационных механизмов в приближенных к реальности условиям с минимизацией всех остальных деталей работы сервера.

Итак, приложения для работы с заказами. Для примера будем использовать такие модели:

```java
public enum OrderStatus {
    PENDING_PAYMENT,
    PAID,
    COMPLETED,
    CANCELED
}

public record CreateOrderRequest(
        @NotNull
        Long productId,

        @NotNull
        @Positive
        BigDecimal paymentAmount,

        @NotNull
        Instant orderedAt
) {
}

public record UpdateOrderRequestV1(
        @NotNull
        Long id,

        @NotNull
        Long productId,

        @NotNull
        @Positive
        BigDecimal paymentAmount,

        @NotNull
        OrderStatus status,

        @NotNull
        Instant orderedAt,

        Instant paidAt,

        Instant completedAt
) {
}

public record SearchOrdersRequest(
        Instant orderedFrom,

        Instant orderedTo,

        Instant paidFrom,

        Instant paidTo,

        Instant completedFrom,

        Instant completedTo,

        @NotNull
        List<OrderStatus> statuses
) {
    @AssertTrue(message = "orderedTo must be after orderedFrom")
    public boolean isOrderedRangeValid() {
        return isValidRange(orderedFrom, orderedTo);
    }

    @AssertTrue(message = "paidTo must be after paidFrom")
    public boolean isPaidRangeValid() {
        return isValidRange(paidFrom, paidTo);
    }

    @AssertTrue(message = "completedTo must be after completedFrom")
    public boolean isCompletedRangeValid() {
        return isValidRange(completedFrom, completedTo);
    }

    private static boolean isValidRange(Instant from, Instant to) {
        return from == null || to == null || to.isAfter(from);
    }
}
```

В общем-то, ничего сложного: создание заказа для какого-то продукта за какую-то стоимость, несложная статусная
модель, которая проходит через серию обновлений заказа (оплата, завершение заказа, либо отмена заказа на каком-то из
этапов). Логика валидации тоже довольно примитивная. В целом, то, что касается использования constraint-аннотаций
внутри моделей, ничем не отличается от уже известных нам подходов в чистом Jakarta Validation: поддерживаются
собственные аннотации, валидация вложенных объектов, группы валидации и так далее.

Но как сообщить Spring, что наши модели необходимо валидировать? На самом деле, достаточно указать возле параметра с
телом запроса (или не аннотированной DTO) аннотацию `@Valid`:

```java
@RestController
@RequestMapping("/v1/orders")
public class OrderControllerV1 {
    @PostMapping
    public ResponseEntity<OrderResponse> create(@Valid @RequestBody CreateOrderRequest request) {
        // ... - Логика создания заказа
    }

    @PutMapping
    public ResponseEntity<OrderResponse> update(@Valid @RequestBody UpdateOrderRequestV1 request) {
        // ... - Логика обновления заказа
    }

    @GetMapping
    // В данном случае все содержимое полей SearchOrdersRequest - параметры запроса, для удобства объединенные в DTO 
    public ResponseEntity<List<OrderResponse>> search(@Valid SearchOrdersRequest filter) {
        // ... - Логика поиска заказов
    }
}
```

В данном примере соответствующий `HandlerMethodArgumentResolver` для каждого из методов определит, что параметр метода 
аннотирован `@Valid` и запустит для него механизм валидации. Если валидация успешна - обработка запроса пойдет дальше.

Если же объект не пройдет валидацию - есть два варианта:

1. В параметрах метода контроллера также есть параметр типа `BindingResult`. В таком случае все найденные нарушения
   будут автоматически записаны в этот объект. Мы, в свою очередь, получим возможность обработать их прямо в
   контроллере - например, чтобы сформировать какой-то специфичный для такой ситуации ответ. Этот подход актуален в
   первую очередь для классического MVC, в REST-модели он практически не используется;
2. Если объекта `BindingResult` в параметрах метода не обнаружено - будет выброшено исключение
   `MethodArgumentNotValidException`. Если оно не будет обработано `@ExceptionHandler`, на уровне HTTP-ответа оно
   будет записано как `400` статус-код ответа.

В статье мы не будем погружаться в API `BindingResult` - он шире, чем обработка результатов валидации. При этом
едва ли вам придется часто сталкиваться с ним на практике. Но с предком `BindingResult` - интерфейсом `Errors` мы
несколько раз столкнемся уже сегодня, он как раз плотно связан с обработкой результатов валидации. Подробнее - в
следующих пунктах.

Кроме `@Valid` в данном разделе справедливо упомянуть использование `@Validated`. В примере выше они взаимозаменяемы -
результат будет идентичен. Однако чаще `@Validated` по отношению к телу запроса используют для валидации с
использованием групп - это мы разберем в отдельном пункте.

### Валидация через `MethodValidationInterceptor`

Второй механизм валидации, доступный в Spring, строится на базе Spring AOP. В принципе, он даже не привязан к
Spring MVC - примеры, которые мы рассмотрим ниже, можно с тем же успехом применить и к сервисному слою, и к любому
другому компоненту. Другой вопрос, что обычно в этом нет необходимости.

Проблема валидации на уровне `HandlerMethodArgumentResolver` в том, что она не покрывает `@RequestParam`,
`@PathVariable` и другие элементы запроса. Справедливости ради, обычно нет необходимости валидировать их через
механизмы Jakarta Validation, но иногда такая потребность возникает.

Допустим, в нашу систему необходимо добавить API для оплаты заказов. Для оплаты нам необходимы номер заказа и сумма
(обязательно должна быть положительной). При этом полезная нагрузка передается отдельными параметрами запроса:

```java
// Ключевой момент в данном механизме - класс должен быть аннотирован @Validated.
// Это та же аннотация, которую мы встретили в предыдущем пункте. Но здесь у нее иная семантика
@Validated
@RestController
@RequestMapping("/v1/payment")
public class PaymentControllerV1 {
    @PostMapping
    // Constraint-аннотации применяются сразу на уровне параметра метода. В данном случае - @Positive.
    // Обратите внимание, что для параметров метода обычно нет смысла прописывать @NotNull - обязательность значения 
    // может регулироваться атрибутом @RequestParam#required()
    public ResponseEntity<Void> pay(@RequestParam Long orderId, @RequestParam @Positive BigDecimal amount) {
        // ... - Логика обработки платежа
    }
}
```

Однако если мы проверим валидацию сейчас - она будет игнорироваться. Для полноты картины не хватает сущности,
которая будет запускать процесс валидации - в предыдущем пункте такой сущностью были объекты
`HandlerMethodArgumentResolver`.

Для того чтобы пример выше заработал, нам необходимо добавить специализированный `BeanPostProcessor` -
`MethodValidationPostProcessor`. В процессе своей инициализации он создает `MethodValidationInterceptor` -
перехватчик вызовов (в терминах Spring AOP больше всего подошел бы термин "advice"), который делегирует проверку
валидатору из Jakarta Validation.

Зарегистрировать `MethodValidationPostProcessor` легко:

```java
@Configuration
@EnableWebMvc
@ComponentScan("com.walking.validation")
public class WebConfig implements WebMvcConfigurer {
    // ... - Другие методы конфигурации, в том числе указанные в предыдущих примерах

    /**
     * Классическая рекомендация для @Bean-методов, создающих пост-процессоры - объявлять методы статическими.
     * Spring умеет обрабатывать такие методы. Если же объявить бин пост-процессора не статично - это приведет
     * к нарушению стандартного процесса инициализации @Configuration-класса, где это произошло.
     * Зачастую это не критично и грозит лишь предупреждениями в логах, но в отдельных случаях может привести
     * к некорректной инициализации контекста - отсутствию у отдельных бинов необходимых прокси или другим артефактам.
     */
    @Bean
    public static MethodValidationPostProcessor methodValidationPostProcessor() {
        return new MethodValidationPostProcessor();
    }
}
```

Теперь пример будет работать, сумма оплаты будет валидироваться на положительное значение.

В случае, если при валидации будут найдены нарушения, `MethodValidationInterceptor` выбросит исключение
`ConstraintViolationException`. Это исключение из Jakarta Validation, внутри оно содержит `Set<ConstraintViolation<?>>`.

На этом этапе стоит отметить несколько нюансов:

- Данный механизм валидации никак не взаимодействует с `BindingResult`. То есть независимо от наличия этого
  параметра в методе контроллера, ошибка валидации в `MethodValidationInterceptor` приведет к исключению. Строго
  говоря, `BindingResult` в принципе имеет значение только для описанной выше валидации через `DataBinder`, в других
  механизмах он не используется;
- В отличие от `MethodArgumentNotValidException`, `ConstraintViolationException` не имеет собственного стандартного
  обработчика в Spring MVC. Во многом из-за того, что это исключение может быть выброшено где угодно, не только при
  валидации метода контроллера. С практической точки зрения это значит, что данное исключение преобразится в `500`
  HTTP-статус, если приложение не обработает ошибку самостоятельно;
- Из-за того, что данный механизм допускаем валидацию нескольких параметров метода, могут возникнуть сложности с
  интерпретацией пути в `ConstraintViolation`. В целом, логика простая: первым узлом указано имя метода контроллера,
  далее - параметр.

В завершение данного пункта стоит отметить, что `MethodValidationInterceptor` позволяет валидировать не только
параметры, но и возвращаемое значение метода - в таком случае constraint-аннотации ставятся над самим методом. Но
эта возможность не так часто используется на практике, поэтому примера в статье не будет.

### Валидация через `InvocableHandlerMethod`

Данный механизм - самый свежий из всех. Он появился в Spring MVC 6.1 и фактически замещает собой валидацию через
`MethodValidationInterceptor` для методов контроллеров.

С точки зрения настроек он отличается лишь двумя пунктами:

1. Не нужно регистрировать `MethodValidationPostProcessor`;
2. Не нужно указывать `@Validated` над классом контроллера.

Иными словами, все сильно проще:)

> Собственно, именно наличие `@Validated` над классом контроллера Spring использует для выбора механизма валидации.
> Если аннотация есть - Spring MVC рассчитывает на валидацию через `MethodValidationInterceptor`. Если вы забыли
> добавить пост-процессор - это ваша проблема, валидация просто проигнорируется.
>
> Если же аннотации над контроллером нет, но constraint-аннотации в методах присутствуют - будет использоваться
> новый механизм на базе `InvocableHandlerMethod`.
>
> Это сделано в первую очередь для того, чтобы избежать двойной валидации одних и тех же данных.

Напишем вторую версию контроллера для оплат, которая использует новый механизм валидации:

```java
@RestController
@RequestMapping("/v2/payment")
public class PaymentControllerV2 {
    @PostMapping
    public ResponseEntity<Void> pay(@RequestParam Long orderId, @RequestParam @Positive BigDecimal amount) {
        // ... - Логика обработки платежа
    }
}
```

Несложно заметить, что разница в коде минимальна.

Но стоит держать в уме, что отличается не только конфигурация - отличается и исключение, которое будет выброшено в
случае невалидных данных.

На смену `ConstraintViolationException` из Jakarta Validation приходит `HandlerMethodValidationException` из Spring
MVC*. У него есть определенные плюсы:

- Стандартный обработчик в Spring MVC, который трактует это исключение как `400` код ответа;
- Привычное для Spring хранение ошибок валидации в `Errors`, что делает обработку ближе к
  `MethodArgumentNotValidException` и позволяет обобщать часть логики. В целом, `MethodArgumentNotValidException`
  более информативен именно для результатов валидации параметров методов.

> *Строго говоря, `HandlerMethodValidationException` часть общего модуля Spring Web, который используется не только
> в MVC, но и в реактивном Spring WebFlux.

Основное, что нужно помнить для этого механизма - то, что он недоступен раньше Spring MVC 6.1.

Если касаться внутреннего устройства механизма - он привязан к `InvocableHandlerMethod`. Мы не сталкивались с ним
ранее напрямую, но сталкивались с его прямым предком - `HandlerMethod`. По сути, каждый раз, когда в логике
`DispatcherServlet` или `RequestMappingHandlerAdapter` речь идет о `HandlerMethod` в разрезе стандартных
классов-контроллеров - на практике будет использован `InvocableHandlerMethod`.

Возвращаясь к основному вопросу, перед самым вызовом целевого метода (в нашем случае - метода контроллера) в
`InvocableHandlerMethod` расположена логика валидации параметров вызываемого метода. А сразу после вызова -
валидация возвращаемого значения. Внутри этой логики мы увидим обращение к объекту `MethodValidator`, который, в
свою очередь:

- делегирует саму валидацию `ExecutableValidator` - интерфейс Jakarta Validation, известный нам из соответствующей
  статьи;
- адаптирует результаты валидации в формат, удобный Spring.

## Spring Validator

В пунктах выше мы рассмотрели основные механизмы, через которые Spring применяет возможности Jakarta Validation к
методам контроллеров. Но стоит также рассмотреть инструмент валидации, не связанный с Jakarta Validation -
собственные валидаторы Spring.

В первую очередь нас будет интересовать интерфейс `org.springframework.validation.Validator`. Он предлагает
реализовать два основных метода:

- `boolean supports(Class<?> clazz)`. Метод позволяет указать, для каких типов данных поддерживается конкретная
  реализация валидатора;
- `void validate(Object target, Errors errors)`. Метод для описания логики валидации. Первый параметр - валидируемый
  объект, второй - уже упомянутый ранее тип `Errors`, необходимый для хранения ошибок валидации.

Такие классы-валидаторы можно рассматривать как альтернативу `@AssertTrue`-методам модели или же альтернативу
собственным constraint-аннотациям уровня класса. В принципе, это нередко удачный компромисс:

- В отличие от `@AssertTrue`-методов, в таких валидаторах работает Spring DI;
- Не нужно захламлять модель;
- Если модель используется в разных контроллерах, при этом правила валидации в них отличаются - валидатор предлагает
  здесь лаконичное решение без нагромождения групп валидации;
- В сравнении с собственной constraint-аннотацией Spring-валидатор - более специализирован, что позволяет не
  переживать о куче одноразовых кастомных аннотаций;
- API `Validator` более дружелюбное, нежели у `ConstraintValidator`. По крайней мере, если не нужны какие-то
  специфические возможности Jakarta Validation.

Рассмотрим применение такого валидатора на примере.

Допустим, мы захотели расширить валидацию при обновлении заказа: очевидно, что в статусе `PENDING_PAYMENT` не должны
заполняться атрибуты `paidAt` и `completedAt`, в то время как в статусе `COMPLETED` - оба атрибута должны быть
заполнены... Попробуем оформить логику валидации полей с датами относительно статусов в коде:

```java
// Как было сказано ранее, Validator поддерживает внедрение Spring-бинов. Например, через объявление класса-валидатор 
// компонентом с внедрением через конструктор или поле. Но в данном примере такой необходимости нет
public class UpdateOrderRequestValidator implements Validator {

    @Override
    // Очевидно, мы хотим применить данный валидатор к модели обновления заказа
    public boolean supports(Class<?> clazz) {
        return UpdateOrderRequestV1.class.isAssignableFrom(clazz);
    }

    @Override
    public void validate(Object target, Errors errors) {
        // На практике Spring-валидаторы обычно работают позже описанных ранее механизмов
        // валидации на базе Jakarta Validation. Если эти механизмы уже нашли какие-то ошибки - чаще всего нет 
        // необходимости проверять запрос еще и через Spring-валидатор.
        // Объект Errors в данном случае полезен тем, что хранит информацию об ошибках
        // валидации на всех пройденных этапах
        if (errors.hasErrors()) {
            return;
        }

        var request = (UpdateOrderRequestV1) target;

        switch (request.status()) {
            case PENDING_PAYMENT -> {
                mustBeEmpty(request.paidAt(), "paidAt", errors);
                mustBeEmpty(request.completedAt(), "completedAt", errors);
            }
            case PAID -> {
                mustBeFilled(request.paidAt(), "paidAt", errors);
                mustBeEmpty(request.completedAt(), "completedAt", errors);
            }
            case COMPLETED -> {
                mustBeFilled(request.paidAt(), "paidAt", errors);
                mustBeFilled(request.completedAt(), "completedAt", errors);
            }
            case CANCELED -> mustBeFilled(request.completedAt(), "completedAt", errors);
        }
    }

    private static void mustBeEmpty(Object value, String field, Errors errors) {
        if (value != null) {
            // Данный метод сохраняет ошибку, относящуюся к конкретному полю. Если ошибку тяжело отнести к одному 
            // атрибуту - обычно используется одна из перегрузок метода reject()
            errors.rejectValue(field, "order.date.mustBeEmpty", "must be empty for this status");
        }
    }

    private static void mustBeFilled(Object value, String field, Errors errors) {
        if (value == null) {
            errors.rejectValue(field, "order.date.mustBeFilled", "must be filled for this status");
        }
    }
}
```

Теперь необходимо зарегистрировать наш валидатор:

```java
@RestController
@RequestMapping("/v1/orders")
public class OrderControllerV1 {
    // С аннотацией @InitBinder мы несколько раз сталкивались ранее. Наверное, регистрацию Spring-валидаторов можно 
    // рассматривать как наиболее популярный способ ее применения в современной разработке. Атрибут аннотации и его 
    // значение будут описаны ниже 
    @InitBinder("updateOrderRequestV1")
    void initUpdateBinder(WebDataBinder binder) {
        // Метод addValidators() позволяет добавить один или несколько валидаторов конкретному биндеру. В данном 
        // случае - биндеру для объекта с типом UpdateOrderRequestV1.
        // Важно не путать метод addValidators() с replaceValidators() или setValidator(). Последние два удалят 
        // существующие валидаторы - например, проверяющий constraint-аннотации в UpdateOrderRequestV1
        binder.addValidators(new UpdateOrderRequestValidator());
    }

    @PutMapping
    public ResponseEntity<OrderResponse> update(@Valid @RequestBody UpdateOrderRequestV1 request) {
        // ... - Логика обновления заказа
    }

    // ... - Другие методы-обработчики запросов
}
```

Теперь кастомный Spring-валидатор будет запускаться после валидации Jakarta-аннотаций и проверять консистентность
статуса и полей с датами.

### `WebDataBinder`

> **!NB**: Этот пункт во многом опционален, поскольку посвящен скорее сущности `DataBinder`, нежели валидации.

Стоит чуть подробнее описать, что происходит в процессе регистрации. Скорее всего это сейчас вызывает много вопросов в
силу слабого представления семантики объектов вроде `DataBinder` и `WebDataBinder`.

> В целом, `DataBinder` и его наследники довольно поверхностно описаны в большинстве обучающих материалов, данный
> курс - не исключение.
>
> В основном это связано с тем, что большая часть семантики этой сущности относится к де-факто устаревшему подходу к
> разработке на базе представлений. Кроме того, зона ответственности в принципе весьма широка и для ее понимания
> нужно хорошо знать множество смежных инструментов Spring MVC. Что само по себе является проблемой для большинства
> разработчиков, не говоря о начинающих специалистах.

`WebDataBinder` в контексте обработки запроса (чаще всего здесь фактически будет фигурировать наследник
`WebDataBinder` - `ExtendedServletRequestDataBinder`) необходим для корректной обработки параметров метода
контроллера.

На каждый вызов HTTP-запроса для почти каждого параметра соответствующего метода контроллера - тела, каждого из
указанных в методе параметров запроса, заголовка и так далее - создается свой объект `WebDataBinder`. Более того,
биндер хранит в себе элемент, к которому он привязан (`DataBinder#target`) и является хранилищем для некоторых иных
объектов (например, `BindingResult`). Это архитектурное решение приводит к тому, что объекты биндера не могут быть
переиспользованы - они живут в пределах обработки конкретного запроса.

В зону ответственности объекта входит:

- Конвертация значений. Скажем, request parameter в сервлетном запросе представлен строкой, а соответствующий ему
  параметр метода контроллера - enum'ом или числом. Аналогично для `@PathVariable`, `@RequestHeader` и ряда других
  параметров;
- Биндинг значений - для `ModelAttribute` и ряда других объектов биндер копирует параметры запроса (query, form-data
  и т.д.) в целевой объект;
- Валидация. И в разрезе валидации на базе Jakarta Validation, и вразрезе применения Spring-валидаторов, вроде 
  описанного выше. В принципе, самому `WebDataBinder` не так важно, кто проводит валидацию под капотом - он лишь 
  позволяет сконфигурировать и запустить список валидаторов. Также это де-факто единственное предназначение
  `WebDataBinder` для `@RequestBody`;
- Сохранение ошибок - здесь `WebDataBinder` управляет упомянутым ранее `BindingResult`;
- Специфика обработки HTML-форм - этой части мы практически не касаемся, она характерна для классического MVC;
- Различная кастомизация правил конвертации и форматирования элементов. Настройка такой кастомизации через
  `PropertyEditor` и `Formatter` - одно из предназначений `@InitBinder`.

Из того, что объектов `WebDataBinder` может быть несколько даже в пределах одного метода контроллера, вытекает
необходимость как-то идентифицировать конкретный биндер при обработке `@InitBinder`-метода. Для этого нужен атрибут
`@InitBinder#value()` - он соотносится с `DataBinder#objectName`.

В случае с `ModelAttribute` для этих целей есть явно заданное имя атрибута. Но для тела запроса такой
формат не подходит - семантически у тела нет собственного имени. Поэтому для таких ситуаций предусмотрено
"вычисляемое" имя - за это отвечает `Conventions.getVariableNameForParameter()` (вызывается в
`RequestResponseBodyMethodProcessor#resolveArgument()`).

В методе `Conventions` можно посмотреть полную логику формирования имени, но в большинстве базовых случаев имя можно
воспринимать как имя класса, записанное с маленькой буквы. По крайней мере, пока тело не представлено
параметризованным типом - для коллекций и других контейнеров логика будет сложнее.

Таким образом, получается, что данный код:

```java
@InitBinder("updateOrderRequestV1")
void initUpdateBinder(WebDataBinder binder) {
    binder.addValidators(new UpdateOrderRequestValidator());
}
```

Находит конкретный биндер c именем `updateOrderRequestV1` и добавляет для него валидатор. С практической точки
зрения здесь есть два нюанса:

1. Это действие происходит при каждом запросе на обновление, в более широком смысле - при каждом запросе в
   контроллере `OrderControllerV1`, у которого есть биндер с именем `updateOrderRequestV1`. Соответственно,
   возникает смысл вынести объект `UpdateOrderRequestValidator` в константу, чтобы не пересоздавать его каждый раз.
   Для валидаторов, являющихся бинами, это не проблема - они по умолчанию синглтоны, для таких легковесных
   валидаторов - адекватная оптимизация;
2. Аргумент в `@InitBinder` не обязателен. Если бы его не было - `initUpdateBinder()` вызывался бы для каждого
   биндера в этом контроллере. И тут может возникнуть конфликт с `Validator#supports()`: если метод вернет `false` 
   для типа объекта, хранящегося в `DataBinder#target` - `DataBinder` выбросит исключение.

## Кастомные валидаторы

Перейдем к более узконаправленным механизмам валидации, которые могут быть полезны в прикладной разработке. Первый из
них - кастомные constraint-аннотации и `ConstraintValidator`'ы.

Сам механизм нам знаком из Jakarta Validation. Однако при использовании `LocalValidatorFactoryBean` нам становится 
доступна инъекция зависимостей в `ConstraintValidator`, как если бы он сам был бином.

Но здесь также важно понимать, что объекты `ConstraintValidator` не регистрируются как singleton-бины - они
инициализируются по флоу, схожему с prototype-бинами. Соответственно, `ConstraintValidator` не проходит полный жизненный
цикл Spring-бина. Хранить в нем состояние тоже все еще не рекомендуется - объектов одной и той же реализации
`ConstraintValidator` в приложении может быть несколько - кэширование в логике Hibernate Validator остается без 
изменений.

Допустим, мы хотим добавить аннотацию, которая будет проверять, что `id` заказа существует в базе данных. В 
классическом `ConstraintValidator` это сделать проблематично - он создается через конструктор без параметров. Однако 
в случае с `LocalValidatorFactoryBean` это возможно:

```java
@Repository
public class OrderRepository {
    /**
     * Заглушка: в проекте нет реальной БД, поэтому считаем, что заказ существует всегда.
     */
    public boolean existsById(Long id) {
        return true;
    }
}

@Documented
@Constraint(validatedBy = ExistedOrderIdValidator.class)
@Target({FIELD, PARAMETER, RECORD_COMPONENT})
@Retention(RUNTIME)
public @interface ExistedOrderId {

    String message() default "order with this id does not exist";

    Class<?>[] groups() default {};

    Class<? extends Payload>[] payload() default {};
}

/**
 * Фабрика создает экземпляр через AutowireCapableBeanFactory, поэтому @Autowired работает так же, как в обычном бине.
 */
public class ExistedOrderIdValidator implements ConstraintValidator<ExistedOrderId, Long> {
    @Autowired
    private OrderRepository orderRepository;

    @Override
    public boolean isValid(Long id, ConstraintValidatorContext context) {
        return id == null || orderRepository.existsById(id);
    }
}

public record UpdateOrderRequestV1(
    @NotNull
    @ExistedOrderId
    Long id

    // ... - Другие поля модели
) {}
```

Аннотация может использоваться наравне с другими constraint'ами, никакой специфики здесь нет.

Однако стоит подсветить концептуальную проблему. С одной стороны, валидации, требующие доступ к базе данных или 
каким-либо иным ресурсам вполне возможны и встречаются на практике. С другой - многие укажут на некорректность 
такого подхода. И тоже будут правы.

Проблема в том, что подобный подход смешивает валидацию ФЛК (форматно-логического контроля) и бизнес-валидацию. Это 
основной аргумент против подобных проверок наличия данных, их уникальности (относительно БД или иного внешнего 
хранилища, а не в пределах одного запроса) или иных сложных валидаций. Такой подход тянет за собой как минимум две 
крупные проблемы:

1. Корректность ошибки, если валидация упадет. Рассмотрим на примере семантики HTTP. Обычно ошибки валидации запроса 
   интерпретируются как `400` код ответа - `Bad Request`. Иными словами, пользователь отправил что-то, не
   соответствующее контракту. Но если мы не нашли в базе `id` сущности - точно ли это `400`? А не, скажем, `404`. 
   Или какой-то еще код, указывающий на проблему ресурса, а не запроса как такового. За пределами HTTP логика та же 
   самая - чаще всего ошибка, определяемая бизнес-валидацией, отличается от той, которая подразумевается под ошибкой 
   валидации в классическом ее представлении; 
2. Валидность результата в бизнес-сценарии. На примере той же проверки существования `id`, мы не можем гарантировать,
   что к моменту выполнения операции обновления `id` все еще будет существовать в БД. В принципе возможна ситуация, 
   когда запись с таким идентификатором была удалена из базы уже после проверки constraint validator'ом, но до того, 
   как обновление фактически применилось в БД. И гарантировать валидность проверки вне открытой транзакции мы не 
   можем. Открывать же транзакцию еще на этапе валидации и держать ее до обновления записи само по себе будет ошибкой 
   проектирования в абсолютном большинстве случаев. В других примерах бизнес-валидации технические причины могут 
   отличаться, но важен сам факт: они есть. 

По совокупности, допустимость бизнес-валидации через валидацию Spring MVC - вопрос дискуссионный. И решается он 
обычно на уровне договоренностей в конкретной команде.

> Имхо, оно того не стоит. Именно такого рода проверки обычно не оправдывают себя и их стоит проводить в бизнес-слое,
> не затаскивая в зону ответственности контроллера.
> 
> При этом остается набор сценариев, в которых внедрение зависимости в `ConstraintValidator` может быть оправдано, 
> но речь будет идти о внедрении бинов, предоставляющих какую-либо утилитарную функциональность для калькуляции или 
> преобразований данных. Если же негативный результат валидации не попадает в семантику `400` кода ответа - это 
> должно быть реализовано иначе.
> 
> Разумеется, данные рассуждения не относятся к ситуациям, когда Jakarta Validation используется для валидации 
> модели БД или каких-либо валидаций в слое бизнес-логики - там общих правил нет, выбор инструмента будет зависеть от 
> конкретной ситуации.

## Группы валидации

Также стоит рассмотреть работу с группами валидаций. В первую очередь - в разрезе валидации через `DataBinder`.

Несложно заметить, что `@Valid` не предполагает указания группы валидации. Соответственно, встает вопрос: как 
обеспечить валидацию тела запроса по группе?

Короткий ответ - `@Validated`. Он предоставляет атрибут `value`, в который можно передать целевые группы валидации.

Более подробно разберем на примере.

Допустим, мы решили переписать API обновления заказов - оставить примерно ту же модель запроса, но сами обновления 
разбить на логические операции: обновление по факту оплаты, обновление по факту выполнения заказа и так далее.

В перспективе это позволит нам сформировать полноценный бизнес-процесс, вместо единого плоского, сложнорегулируемого 
обновления. Заодно позволит избавиться от Spring Validator'а, заменив его на декларативную валидацию с использованием 
групп.

Перепишем модель с учетом групп валидации:

```java
public record UpdateOrderRequestV2(
    @NotNull
    Long id,

    @NotNull
    Long productId,

    @NotNull
    @Positive
    BigDecimal paymentAmount,

    @NotNull
    OrderStatus status,

    @NotNull
    Instant orderedAt,

    @Null(groups = PendingPayment.class)
    @NotNull(groups = {Paid.class, Completed.class})
    Instant paidAt,

    @Null(groups = {PendingPayment.class, Paid.class})
    @NotNull(groups = {Completed.class, Canceled.class})
    Instant completedAt
) {
    /**
     * Наследование группы валидации от jakarta.validation.groups.Default -
     * стандартный способ избавиться от явного указания дефолтной группы. Если этого не сделать
     * и не указывать Default-группу явно в значении атрибута @Validated -
     * аннотации без группы будут игнорироваться валидатором. Эта тема ранее затрагивалась в статье, посвященной
     * Jakarta Validation
     */
    public interface PendingPayment extends Default {
    }

    public interface Paid extends Default {
    }

    public interface Completed extends Default {
    }

    public interface Canceled extends Default {
    }
}
```

Затем напишем новую версию контроллера - она будет содержать только операции обновления, создание и поиск останутся 
доступны через первую версию:

```java
@RestController
@RequestMapping("/v2/orders")
public class OrderControllerV2 {

    @PutMapping("/pending-payment")
    public ResponseEntity<OrderResponse> updateToPendingPayment(
            @Validated(UpdateOrderRequestV2.PendingPayment.class) @RequestBody UpdateOrderRequestV2 request) {
        // ... - Логика обновления заказа
    }

    @PutMapping("/paid")
    public ResponseEntity<OrderResponse> updateToPaid(
            @Validated(UpdateOrderRequestV2.Paid.class) @RequestBody UpdateOrderRequestV2 request) {
        // ... - Логика обновления заказа
    }

    @PutMapping("/completed")
    public ResponseEntity<OrderResponse> updateToCompleted(
            @Validated(UpdateOrderRequestV2.Completed.class) @RequestBody UpdateOrderRequestV2 request) {
        // ... - Логика обновления заказа
    }

    @PutMapping("/canceled")
    public ResponseEntity<OrderResponse> updateToCanceled(
            @Validated(UpdateOrderRequestV2.Canceled.class) @RequestBody UpdateOrderRequestV2 request) {
        // ... - Логика обновления заказа
    }
}
```

В целом, правки достаточно тривиальные. Основная идея - необходимость использования групп валидации приводит к 
использованию `@Validated`.

> Стоит дополнительно отметить, что подобный API - пример плохого дизайна. Каждый запрос на обновление требует пачки 
> избыточных полей, при этом достаточно ввести несколько моделей для обновления в разных ситуациях и сразу исчезнет 
> проблема сложной валидации. Более классическим примером может послужить объединение моделей для создания и 
> обновления заказа, но похожий пример мы уже рассматривали в статье, посвященной Jakarta Validation, поэтому не будем 
> повторяться.

## Использование в RestClient

Еще один пример возможного использования инструментов Jakarta Validation в Spring MVC - валидация ответа в 
`RestClient`. Здесь практически нет декларативной составляющей, поскольку подобный механизм не предусмотрен из
коробки - с валидатором придется работать императивно.

Допустим, мы описываем логику обработки платежа. При этом сам платеж обрабатывает другое приложение - некий внешний 
сервис. У нас есть определенный контракт коммуникации, при этом нам важно гарантировать, что ответы этого сервиса 
соответствуют контракту. Существует два базовых способа сделать это:

1. Валидация в interceptor'е. Этот подход мы рассматриваем в примере ниже.
2. Создание собственной обертки над `RestClient`, в которой валидация ответа будет происходить уже после логики 
   самого `RestClient`. Это решение более громоздкое, но оно позволяет не думать о многократном чтении ответа и 
   проблемах его десериализации. Ведь Jakarta Validation работает с Java-объектами, а не потоками данных. И если 
   `RestClient` используется для нескольких различных запросов, в интерцепторе надо как-то определять, в какой 
   Java-тип надо десериализовать тело ответа перед валидацией. 

Итак, приступаем к реализации. Сконфигурируем `RestClient`:

```java
@Configuration
public class RestClientConfig {
    private static final String PAYMENT_SERVICE_URL = "https://my-payment-service.com";

    @Bean
    public RestClient paymentRestClient(ErrorHandlingInterceptor errorHandlingInterceptor,
                                        ResponseValidationInterceptor validationInterceptor,
                                        PaymentMockInterceptor mockInterceptor) {
        return RestClient.builder()
            .baseUrl(PAYMENT_SERVICE_URL)
            // Как и в Servlet API, изначально тело (в данном случае - ответа) можно вычитать лишь единожды.
            // Такая обертка для ClientHttpRequestFactory - один из стандартных способов решить эту проблему
            // через буферизацию тела. Допустимо, если ответы не слишком объемные и приложение может себе
            // позволить держать их в памяти целиком
            .requestFactory(new BufferingClientHttpRequestFactory(new SimpleClientHttpRequestFactory()))
            // Дополнительный интерцептор с перехватом исключений. Подробнее описано ниже
            .requestInterceptor(errorHandlingInterceptor)
            // Интерцептор, непосредственно ответственный за валидацию
            .requestInterceptor(validationInterceptor)
            // Еще один интерцептор на случай, если вам захочется проверить логику локально - мокает ответ, поскольку 
            // реального внешнего сервиса не существует. Листинг в примере не приложен, но его можно найти в репозитории,
            // указанном в конце статьи
            .requestInterceptor(mockInterceptor)
            .build();
    }
}
```

Добавим реализацию интерцептора-валидатора:

```java
@Component
public class ResponseValidationInterceptor implements ClientHttpRequestInterceptor {
    public static final String RESPONSE_TARGET_TYPE = "responseTargetType";

    private final ObjectMapper objectMapper;
    private final Validator validator;

    public ResponseValidationInterceptor(ObjectMapper objectMapper, Validator validator) {
        this.objectMapper = objectMapper;
        this.validator = validator;
    }

    @Override
    public ClientHttpResponse intercept(HttpRequest request, byte[] body, ClientHttpRequestExecution execution)
            throws IOException {
        ClientHttpResponse response = execution.execute(request, body);

        // Если в ответе ошибка - валидация тела для позитивного сценария не имеет смысла,
        // едва ли в теле будет нужный объект
        if (!response.getStatusCode().is2xxSuccessful()) {
            return response;
        }

        // Получаем тип тела ответа из атрибута запроса.
        // Соответственно, при формировании запроса тип должен быть передан в атрибут
        var responseType = (TypeReference<?>) request.getAttributes()
                .get(RESPONSE_TARGET_TYPE);

        // Будем считать, что если тип тела ответа не передан - валидация не требуется
        if (responseType == null) {
            return response;
        }

        Object responseBody = objectMapper.readValue(response.getBody(), responseType);

        Set<ConstraintViolation<Object>> violations = validator.validate(responseBody);
        if (!violations.isEmpty()) {
            throw new ConstraintViolationException("Invalid response from external service", violations);
        }

        return response;
    }
}
```

> Стоит отметить, что решение на базе атрибутов запроса возможно, начиная со Spring MVC 6.2.

Также опишем логику вызова `RestClient` и вспомогательные модели:

```java
@Service
public class PaymentService {
    private static final TypeReference<PaymentResponse> RESPONSE_TYPE_REFERENCE = new TypeReference<>() {};

    private final RestClient paymentRestClient;

    public PaymentService(RestClient paymentRestClient) {
        this.paymentRestClient = paymentRestClient;
    }

    public PaymentResponse pay(Long orderId, BigDecimal amount) {
        return paymentRestClient.post()
                .uri("/payments")
                .body(new PaymentRequest(orderId, amount))
                // Установка атрибута для интерцептора-валидатора
                .attribute(ResponseValidationInterceptor.RESPONSE_TARGET_TYPE, RESPONSE_TYPE_REFERENCE)
                .retrieve()
                .body(PaymentResponse.class);
    }
}

public record PaymentRequest(
        Long orderId,
        BigDecimal amount
) {
}

public record PaymentResponse(
        @NotNull
        Instant processedAt,
        @NotNull
        Integer transactionId
) {
}
```

Сценарий использования довольно простой. На уровне вызова валидатора все тоже достаточно примитивно: десериализация 
ответа и вызов самой валидации. Если обнаружены ошибки - исключение.

Добавим описание интерцептора, обрабатывающего ошибки:

```java
@Component
public class ErrorHandlingInterceptor implements ClientHttpRequestInterceptor {
    private static final String ERROR_MESSAGE = "Error response from external service";

    @Override
    public ClientHttpResponse intercept(HttpRequest request, byte[] body, ClientHttpRequestExecution execution) {
        try {
            ClientHttpResponse response = execution.execute(request, body);

            // Упрощенная модель. Разумеется, для такой логики существуют специализированные StatusHandler'ы,
            // однако в разрезе основной темы это не так важно 
            if (response.getStatusCode().isError()) {
                throw new IllegalStateException("Unexpected status " + response.getStatusCode());
            }

            return response;
        } catch (IOException | RuntimeException e) {
            // Ключевой момент - общее исключение для ошибок обработки запроса. В данном случае использован
            // RuntimeException, инкапсулирующий в себе информацию о фактической ошибке.
            // В реальном проекте это было бы собственное бизнес-исключение. Ключевой момент - для приложения чаще
            // всего важно знать, что при обращении к внешней системе произошла ошибка.
            // А вот какая конкретно ошибка - приложению чаще всего безразлично. Поэтому общее высокоуровневое
            // исключение зачастую будет удобнее в дальнейшей обработке. Технические детали будут важны для
            // разработчика при анализе проблемы, но для этого достаточно сохранить оригинальную ошибку в cause     
            throw new RuntimeException(ERROR_MESSAGE, e);
        }
    }
}
```

Таким образом у нас получилось решение, которое динамически определяет тип тела ответа и на базе него валидирует 
реальный ответ. При этом ошибка валидации, как и ряд других ошибок в результате выполнения запроса будет скрыта 
общим бизнес-исключением, что упрощает обработку негативных сценариев на уровне классов, обращающихся к `RestClient`.

## Обработка ошибок валидации в контроллерах

Реальные системы часто подразумевают жесткие контракты ответов даже в случае ошибок. Это позволяет и упростить
обработку ошибок на стороне клиента, и сообщить необходимые детали ошибки в удобном для автоматизированной обработки
формате, и при этом избежать раскрытия технических деталей, о которых клиенту знать не нужно.

Для полноты картины обработке ошибок в Spring MVC будет посвящена отдельная статья. Однако в завершение темы валидации
стоит рассмотреть пример обработки `MethodArgumentNotValidException`, `HandlerMethodValidationException` и
`ConstraintViolationException`.

В данном случае рассмотрим, как мы можем обобщить информацию из разных ошибок валидации, возникших при использовании
различных механизмов.

Для начала определим формат ответа в случае ошибки валидации:

```java
// Фактически - список ошибок, с указанием конкретного элемента и описанием самой ошибки 
public record ErrorModel(List<Violation> violations) {
    public record Violation(String field, String message) {
    }
}
```

Теперь опишем сами обработчики:

```java
// Логику и особенности использования @ControllerAdvice и @RestControllerAdvice подробнее рассмотрим в отдельной 
// статье. На данном этапе можно воспринимать это как глобальный обработчик ошибок для всех контроллеров приложения
@RestControllerAdvice
public class GlobalExceptionHandler {

    /**
     * Аннотацию @ExceptionHandler мы уже рассматривали ранее, но в разрезе конкретного контроллера. Здесь логика та 
     * же, но зона применения - все приложение. 
     *
     * Используется для ошибок в OrderControllerV1 (@Valid и кастомный Spring-валидатор)
     * и OrderControllerV2 (@Validated для @RequestBody)
     */
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorModel> handle(MethodArgumentNotValidException e) {
        return badRequest(toViolations(e.getBindingResult()));
    }

    /**
     * Используется для ошибок валидации @RequestParam в PaymentControllerV2. Актуально именно для реализации
     * без @Validated над классом, доступно в Spring MVC 6.1+
     */
    @ExceptionHandler(HandlerMethodValidationException.class)
    public ResponseEntity<ErrorModel> handle(HandlerMethodValidationException e) {
        List<Violation> violations = new ArrayList<>();

        // Как было упомянуто ранее, у HandlerMethodValidationException широкие возможности по репрезентации ошибок. 
        // В данном случае мы можем увидеть весь список ошибок валидации с метода контроллера, сгруппированные по 
        // параметрам метода.
        // Отдельно стоит отметить, что метод getParameterValidationResults() появился в 6.2, для версии 6.1 решение 
        // выглядело бы чуть иначе с использованием метода getAllValidationResults() (deprecated в 6.2)
        e.getParameterValidationResults()
                // Тип параметра result - ParameterValidationResult
                .forEach(result -> {
                    // В ParameterValidationResult ошибки на вложенных объектах упаковываются в знакомый нам Errors.
                    // Если для параметра метода были напрямую применены constraint-аннотации (как в методе 
                    // PaymentControllerV2) - они сохраняются в объект MessageSourceResolvable, который можно 
                    // увидеть ниже 
                    if (result instanceof Errors errors) {
                        violations.addAll(toViolations(errors));
                        return;
                    }

                    // Ранее упоминалось, что группировка ошибок в HandlerMethodValidationException сделана удобнее, 
                    // чем в ConstraintViolationException. Здесь видно, что мы можем получить конкретный объект 
                    // MethodParameter, содержащие все метаданные проблемного параметра
                    String parameter = result.getMethodParameter()
                            .getParameterName();
                    for (MessageSourceResolvable error : result.getResolvableErrors()) {
                        // MessageSourceResolvable#getDefaultMessage() предоставляет описание конкретного нарушения. 
                        // В нашем случае здесь будет значение message нарушенных constraint-аннотаций
                        violations.add(new Violation(parameter, error.getDefaultMessage()));
                    }
                });

        return badRequest(violations);
    }

    /**
     * Используется для ошибок валидации @RequestParam в PaymentControllerV1 - в сценарии с указанием @Validated
     * над классом контроллера. Для Spring MVC младше версии 6.1 - стандартный подход,
     * в более свежих версиях Spring - допустимый, но фактически рудиментарный.
     * <p>
     * В более широком смысле этот обработчик отлавливает стандартное исключение Jakarta Validation, если оно не было
     * чем-либо обернуто. Например, он бы применялся к исключению, выбрасываемому
     * в ResponseValidationInterceptor, если бы оно не отлавливалось отдельно
     */
    @ExceptionHandler(ConstraintViolationException.class)
    public ResponseEntity<ErrorModel> handle(ConstraintViolationException e) {
        List<Violation> violations = e.getConstraintViolations()
                .stream()
                .map(v -> new Violation(v.getPropertyPath().toString(), v.getMessage()))
                .toList();

        return badRequest(violations);
    }

    private static List<Violation> toViolations(Errors errors) {
        // Здесь можно увидеть работу с Errors. Ранее упоминалось различие reject() и rejectValue() методов. Здесь 
        // другая сторона этой же медали - получение отдельно списков ошибок в конкретных атрибутах (getFieldErrors)
        // и ошибок, привязанных к объекту целиком (getGlobalErrors())
        var fieldErrorStream = errors.getFieldErrors()
                .stream()
                // Если можем - указываем конкретный атрибут
                .map(error -> new Violation(error.getField(), error.getDefaultMessage()));

        var globalErrorStream = errors.getGlobalErrors()
                .stream()
                // Если нет - указываем имя самого объекта. Для Jakarta-валидаций актуально для constraint'ов над 
                // классами
                .map(error -> new Violation(error.getObjectName(), error.getDefaultMessage()));

        return Stream.concat(fieldErrorStream, globalErrorStream)
                .toList();
    }

    private static ResponseEntity<ErrorModel> badRequest(List<Violation> violations) {
        // Для всех ошибок валидации используем 400 код ответа
        return ResponseEntity.status(HttpStatus.BAD_REQUEST)
                .body(new ErrorModel(violations));
    }
}
```
